# Optimisation Registry

Created: 2026-09-15 11:06:57 IST  
Last updated: 2026-09-15 16:06:33 IST
Related tasks: `KUN-083`, `KUN-090`, `KUN-093`, `KUN-094`, `KUN-098`, `KUN-101`, `KUN-102`, `KUN-103`
Status: registry-backed storage and project/repo CLI execution for published rules.

[`optimisations.json`](../registry/optimisations.json) is the single source of truth for developer-machine storage optimisation definitions. It covers the 13 categories researched in [`developer-cleanup-targets.md`](developer-cleanup-targets.md), plus targeted gaps found in the existing storage code. A rule has a stable ID, lifecycle status, display copy, scope, target selector, optional probe commands, review policy, live validators, action descriptor, and source references. Repeated targets have one canonical rule: SwiftPM `.build` belongs to project-generated files, while Maven and Gradle shared stores belong to JVM.

The live registry is `schemaVersion: 2` and `integration: engine_ready`. `kundol optimise storage|projects|repos` loads it through the engine under [`src/services/optimisation-registry`](../src/services/optimisation-registry). The 12 published rules can be probed; 83 proposals stay inactive. The engine identifies precise targets, presents identity, size, evidence, sources, action, and safety tier for review, then re-identifies and validates each selected live target before acting and auditing. It deduplicates overlapping physical paths and resource IDs, keeping the stricter safety tier. These are the only public cleanup routes.

| JSON field | Meaning |
|---|---|
| `integration` | `catalogue_only` blocks engine execution; `engine_ready` permits published rules and opted-in beta rules with complete code handlers. |
| `categories` | Stable category IDs and human labels for plan grouping. |
| `sources` / `sourceRefs` | Official or owner-maintained source URLs, linked from each rule. |
| `id`, `categoryId`, `label`, `description` | Stable rule identity and concise user-facing copy. |
| `status` | Registry-backed lifecycle: `proposed` (researched catalogue entry), `wip` (adapter/flow under development), `beta` (tested experimental CLI path), or `published` (supported CLI path). Current rules include 12 published and 83 proposed. |
| `scope`, `selector` | Where to inventory and how to identify an exact generated path, tool cache, or owner-tool resource. |
| `probeCommands` | Optional structured argument arrays used for read-only inventory. |
| `review` | `safe` suggested, `review` explicit selection, or `protected` inventory only; `forceEligible` is false for review and protected rules. |
| `validators` | Checks the engine must repeat immediately before apply, including existence, activity, path containment, project markers, and resource-use evidence. |
| `action` | A structured owner-tool adapter, fixed argument array, generated-path removal, or `none`. |
| `messageTemplates` | Shared plan, success, skipped, and failure output templates. |

The JSON describes actions; it is not an executable shell script. Structured `argv` entries and adapters require dedicated process execution and code-owned safety checks. `generated_path` names are literal filenames; `generated_suffix` is for typed, owner-verified suffix targets such as `.egg-info` and `.profraw`. Published generated-path rules are active in project/repo cleanup; suffix rules remain proposed. `protected` rules must use `selection: none` and `action: none`, including Docker volumes, VM disks, Open WebUI data, Git metadata, Xcode archives, app support/container data, and macOS System Data. The validator rejects shell command forms, duplicate IDs, missing category/source references, and suggested generated-path removal without live path, symlink, marker, and activity checks.

Contributors can [request a target](https://github.com/vikz91/kundol/issues/new?title=%5BRegistry%20request%5D%3A%20&body=Owning%20tool%3A%0A%0AExact%20target%20and%20scope%3A%0A%0AOwner%20documentation%3A%0A%0AWhy%20add%20it%3A%0A%0AData%20and%20safety%20risks%3A%0A) before implementing it; the structured [issue form](../.github/ISSUE_TEMPLATE/registry_request.yml) is available from GitHub's chooser on `main`. `bun run registry:new -- --help` shows the entry-scaffold options; the command appends a source and a valid `proposed`, protected inventory rule to this JSON file without reformatting existing entries. Its adapter selector is a placeholder and its action is `none`. A registry-only PR can refine or publish a proposal when its selector, validators, action, marker, target kind, and review tier already satisfy code-owned policies. A new adapter, removable name, or resource type needs code and tests; an unimplemented adapter must never silently fall back to directory deletion. A status change to `beta` or `published` requires an implemented, tested registry-backed CLI flow. Keep sources specific to the target and distinguish removable generated data from configuration or user data.

The 19 additions cover Bun, pnpm, and Yarn shared caches; Parcel, configured tool caches, ESLint, TypeScript, Python, Go, .NET, LLVM, and Rust project artifacts; Python test and virtual environments; and a protected user-cache inventory. Their `sourceRefs` point to owner documentation for the named path or tool action. The existing 76 rules were checked against their owner sources as well. This audit tightened several claims: NuGet's documented command clears the whole global package store, Playwright's documented uninstall is installation-scoped, Colima's ordinary profile delete preserves its data disk, and kind images belong to a container engine. Ambiguous output and retained reports use explicit review or protected inventory; source citations establish targets and tool behavior, while ownership checks remain requirements for future adapters.

The engine takes explicit project roots and approved user roots; it never discovers the whole home directory on its own. The project CLI discovers roots to depth 7 from marker patterns in published JSON rules, skipping symlink, generated, and protected directories. Generated removal requires code-approved names or suffixes, matching owner markers, an exact file/directory kind, and a minimum review tier. Tool-cache path probes and command actions run only exact code-approved argument lists bound to their owner selectors and minimum tiers, with bounded output and a timeout. Owner-resource selectors, actions, and validators require registered code handlers; selectors must return an owner ID, resource ID, and fingerprint, and missing IDs fail closed. `proposed` and `wip` rules stay inactive; the CLI has no beta opt-in yet; published rules are eligible only with `integration: engine_ready`.

The CLI prints every candidate with its tier, path, size, action, description, and source. Answer `y` to select safe suggestions, enter displayed numbers to select review targets explicitly, or leave blank to cancel; `-f` selects only eligible safe targets. Protected inventory cannot be selected. Apply consumes an engine-issued review plan once, re-probes each selected generated/tool-cache path instead of whole rules, compares device/inode or resource fingerprints, repeats registered validators, and writes per-target attempt/outcome rows to SQLite plus session audit events. One run-scoped SQLite connection records target events, with no connection held during the selection prompt. A failed attempt audit stops the action; an outcome audit failure appears in `auditWarnings` alongside the actual action result. CLI and engine tests use disposable projects and an injected owner-command runner. Published CLI bindings use a conservative seven-day no-change check that streams target directory entries and refuses trees over 150,000 entries; this detects recent activity, but cannot prove that no process has an old file open.

Physical directory size measurement follows eligibility checks and stops after 50,000 entries; an incomplete footprint stays unknown rather than reporting a partial number. Generated-path deletion uses an isolated system-Python helper with [descriptor-relative `os` operations](https://docs.python.org/3/library/os.html). It opens each path ancestor with no-follow flags and deletes within opened directory descriptors, preventing a symlinked ancestor from redirecting deletion outside the reviewed tree. It refuses to act when the helper or descriptor support is unavailable. A final leaf-name replacement between inode verification and POSIX unlink remains possible within the anchored parent; the helper does not claim inode-atomic deletion. Resource adapters still re-query their owner inventory per selected resource until their APIs support a targeted lookup.

Run `bun run registry:check` before a PR. `bun run check` includes that command and regression tests. Broad Docker prune and unattributed top-level temp deletion are no longer routed through the public storage CLI; their proposed registry rules need scoped owner adapters and tests before publication.
