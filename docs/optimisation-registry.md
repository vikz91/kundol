# Optimisation Registry

Created: 2026-09-15 11:06:57 IST  
Last updated: 2026-09-17 12:00:00 IST
Related tasks: `KUN-083`, `KUN-090`, `KUN-093`, `KUN-094`, `KUN-098`, `KUN-101`, `KUN-102`, `KUN-103`
Status: registry-backed storage and project/repo CLI execution for published rules.

[`optimisations.json`](../registry/optimisations.json) is the single source of truth for developer-machine storage optimisation definitions. It covers the 13 categories researched in [`developer-cleanup-targets.md`](developer-cleanup-targets.md), plus targeted gaps found in the existing storage code. A rule has a stable ID, lifecycle status, display copy, scope, target selector, optional probe commands, review policy, live validators, action descriptor, and source references. Repeated targets have one canonical rule: SwiftPM `.build` belongs to project-generated files, while Maven and Gradle shared stores belong to JVM.

The live registry is `schemaVersion: 2` and `integration: engine_ready`. `kundol optimise storage|projects|repos|docker` loads one scope through the engine under [`src/services/optimisation-registry`](../src/services/optimisation-registry); `optimise all --workdir <path> --docker-context <name>` composes all four scopes into one plan. The published subset can be probed; 64 beta entries stay catalogue-only; five exact code-approved beta IDs require `--allow-beta`. The engine identifies precise path or owner-resource targets, presents identity, size, evidence, sources, action, and safety tier for review, then re-identifies and validates each selected live target before acting and auditing. It deduplicates overlapping physical paths and resource IDs, keeping the stricter safety tier. The combined route additionally fails closed if targets overlap across scope-specific engines. Docker always requires an explicit named context; no Docker-context rule is published yet.

| JSON field | Meaning |
|---|---|
| `integration` | `catalogue_only` blocks engine execution; `engine_ready` permits published rules. An opted-in beta also needs code-owned executable approval, which only five of the current 69 have. |
| `categories` | Stable category IDs and human labels for plan grouping. |
| `sources` / `sourceRefs` | Official or owner-maintained source URLs, linked from each rule. |
| `id`, `categoryId`, `label`, `description` | Stable rule identity and concise user-facing copy. |
| `status` | Registry-backed lifecycle: `proposed` (researched catalogue entry), `wip` (adapter/flow under development), `beta` (experimental testing catalogue; not executable by status alone), or `published` (supported CLI path). Use `kundol tools list --status <status>` for the live count; [the 75-rule programme](registry-75-implementation-plan.md) tracks the baseline and split replacements. |
| `scope`, `selector` | Where to inventory and how to identify an exact generated path, tool cache, or owner-tool resource. |
| `probeCommands` | Optional structured argument arrays used for read-only inventory. |
| `review` | `safe` suggested, `review` explicit selection, or `protected` inventory only; `forceEligible` is false for review and protected rules. |
| `validators` | Checks the engine must repeat immediately before apply, including existence, activity, path containment, project markers, and resource-use evidence. |
| `action` | A structured owner-tool adapter, fixed argument array, generated-path removal, or `none`. |
| `messageTemplates` | Shared plan, success, skipped, and failure output templates. |

The JSON describes actions; it is not an executable shell script. Structured `argv` entries and adapters require dedicated process execution and code-owned safety checks. `generated_path` names are literal filenames; `generated_suffix` is for typed, owner-verified suffix targets such as `.egg-info` and `.profraw`. Published generated-path and explicit-review generated-suffix rules are active in project/repo cleanup. `protected` rules must use `selection: none` and `action: none`, including Docker volumes, VM disks, Open WebUI data, Git metadata, Xcode archives, app support/container data, and macOS System Data. The validator rejects shell command forms, duplicate IDs, missing category/source references, and suggested generated-path removal without live path, symlink, marker, and activity checks.

`--allow-beta` is a CLI opt-in, not blanket beta execution. The code-owned [beta execution manifest](../src/services/optimisation-registry/beta-execution.ts) permits only these exact bindings:

| Beta ID | Route | Effect with opt-in |
|---|---|---|
| `store.yarn.cache` | `storage` | Yarn Classic 1.x exact-cache review from a selected package workspace; modern/delegated Yarn is rejected and the whole-cache owner action requires displayed-number selection. |
| `project.python.virtual_envs`, `project.python.test_envs` | `projects` / `repos` on Linux | Exact Python environment review; a displayed-number selection and live owner/process checks are required. macOS skips because native process visibility is unverified. |
| `docker.network.unused`, `docker.volume.unused` | `docker <context>` | Read-only protected inventory in one pinned named context; neither can be selected or removed. |

All other 64 beta IDs fail closed before owner probes. With beta opt-in, every unavailable rule in the selected route is printed by ID and reason rather than hidden behind a count. Scoped routes remain scoped: `storage` does not run workdir, system, or Docker-context rules. The explicit `all` route attempts the readiness gate for every rule in all four scopes, but does not bypass the code-owned manifest. `-f` still selects only safe, force-eligible published candidates.

Contributors can [request a target](https://github.com/vikz91/kundol/issues/new?title=%5BRegistry%20request%5D%3A%20&body=Owning%20tool%3A%0A%0AExact%20target%20and%20scope%3A%0A%0AOwner%20documentation%3A%0A%0AWhy%20add%20it%3A%0A%0AData%20and%20safety%20risks%3A%0A) before implementing it; the structured [issue form](../.github/ISSUE_TEMPLATE/registry_request.yml) is available from GitHub's chooser on `main`. `bun run registry:new -- --help` shows the entry-scaffold options; the command appends a source and a valid `proposed`, protected inventory rule to this JSON file without reformatting existing entries. Its adapter selector is a placeholder and its action is `none`. A registry-only PR can refine or publish a proposal when its selector, validators, action, marker, target kind, and review tier already satisfy code-owned policies. A new adapter, removable name, or resource type needs code and tests; an unimplemented adapter must never silently fall back to directory deletion. A status change to `published` requires an implemented, tested registry-backed CLI flow. The current 69-rule beta cohort is a testing track; only five exact IDs have code-owned approval behind `--allow-beta`, and status alone cannot create a handler. Keep sources specific to the target and distinguish removable generated data from configuration or user data.

The 19 additions cover Bun, pnpm, and Yarn shared caches; Parcel, configured tool caches, ESLint, TypeScript, Python, Go, .NET, LLVM, and Rust project artifacts; Python test and virtual environments; and a protected user-cache inventory. Their `sourceRefs` point to owner documentation for the named path or tool action. The existing 76 rules were checked against their owner sources as well. This audit tightened several claims: NuGet's documented command clears the whole global package store, Playwright's documented uninstall is installation-scoped, Colima's ordinary profile delete preserves its data disk, and kind images belong to a container engine. Ambiguous output and retained reports use explicit review or protected inventory; source citations establish targets and tool behavior, while ownership checks remain requirements for future adapters.

The engine takes explicit project roots and approved user roots; it never discovers the whole home directory on its own. The project CLI discovers roots to depth 7 from marker patterns in published JSON rules, skipping symlink, generated, and protected directories. Generated removal requires code-approved names or suffixes, matching owner markers, an exact file/directory kind, and a minimum review tier. Tool-cache path probes and command actions run only exact code-approved argument lists bound to their owner selectors and minimum tiers, with bounded output and a timeout. Owner-resource selectors, actions, and validators require registered code handlers; selectors must return an owner ID, resource ID, and fingerprint, and missing IDs fail closed. `proposed` and `wip` stay inactive. `--allow-beta` includes only approved Yarn Classic cache review, Linux Python project reviews, and protected Docker network/volume inventories; an unapproved beta ID remains inactive. Published rules are eligible only with `integration: engine_ready`.

The CLI prints every candidate with its tier, path, size, action, description, and source. Answer `y` to select safe suggestions, enter displayed numbers to select review targets explicitly, or leave blank to cancel; `-f` selects only eligible safe targets. Protected inventory cannot be selected. Apply consumes an engine-issued review plan once, re-probes each selected generated/tool-cache path instead of whole rules, compares device/inode or resource fingerprints, repeats registered validators, and writes per-target attempt/outcome rows to SQLite plus session audit events. One run-scoped SQLite connection records target events, with no connection held during the selection prompt. A failed attempt audit stops the action; an outcome audit failure appears in `auditWarnings` alongside the actual action result. CLI and engine tests use disposable projects and an injected owner-command runner. Published CLI bindings use a conservative seven-day no-change check that streams target directory entries and refuses trees over 150,000 entries; this detects recent activity, but cannot prove that no process has an old file open.

Physical directory size measurement follows eligibility checks and stops after 50,000 entries; an incomplete footprint stays unknown rather than reporting a partial number. Generated-path deletion uses an isolated system-Python helper with [descriptor-relative `os` operations](https://docs.python.org/3/library/os.html). It opens each path ancestor with no-follow flags and deletes within opened directory descriptors, preventing a symlinked ancestor from redirecting deletion outside the reviewed tree. It refuses to act when the helper or descriptor support is unavailable. A final leaf-name replacement between inode verification and POSIX unlink remains possible within the anchored parent; the helper does not claim inode-atomic deletion. Adapters with a targeted owner lookup re-identify selected resources without repeating the full inventory; legacy function adapters still re-enumerate.

Local handlers are registered through the code-owned [`local-handler-bindings.ts`](../src/services/optimisation-registry/local-handler-bindings.ts) manifest, which pairs each exact rule, selector, action, and live validator set. A JSON adapter ID cannot create a handler by itself. Code-owned adapters with `{ list, lookup }` re-identify only the selected owner resource at apply; legacy function adapters still re-enumerate and should be migrated. Read-only rule probes run at bounded concurrency, while actions remain sequential and audited.

Run `bun run registry:check` before a PR. `bun run check` includes that command, `bun run registry:programme` baseline-presence check, and regression tests. The stricter `bun run registry:release` must pass before the 75-rule implementation PR; it fails while any baseline proposal or mapped replacement is unpublished. Broad Docker prune and unattributed top-level temp deletion are not routed through storage or Docker context; their beta catalogue rules need scoped owner adapters and disposable owner tests before publication.
